## Análisis Técnico: Módulo de Transmisión Real-Time y Optimización de Consultas SQL

El módulo de rendimiento de QuestFest reemplaza los esquemas tradicionales de consulta periódica (*short-polling*) por dos mecanismos de ingeniería de software de alto rendimiento:

1. **Transmisión Unidireccional en Tiempo Real mediante Server-Sent Events (SSE)**:
   Implementado en el endpoint `/api/feed/stream` de `app/api/routers/publicaciones.py`, utiliza la interfaz `StreamingResponse` de FastAPI y un publicador de eventos asíncrono basado en colas de memoria (`app/core/events.py`). En entornos con servidores persistentes (como Docker Compose), cuando un usuario publica un mensaje o el sistema genera una notificación automática, el servidor emite una trama `text/event-stream` inmediatamente a todos los clientes suscritos.

2. **Sondeo Inteligente Adaptativo para Entornos Serverless (`useFeedStream.ts`)**:
   En arquitecturas sin servidor (Vercel Lambdas), donde las instancias carecen de memoria compartida y las conexiones de streaming son cortadas tras los límites de timeout perimetral, el sistema implementa un mecanismo de sondeo reactivo optimizado en `frontend/src/hooks/useFeedStream.ts`:
   - **Page Visibility API**: El hook detecta el estado de visibilidad del documento (`document.visibilityState`). Si el usuario minimiza la pestaña o cambia de aplicación móvil, el temporizador de 15 segundos se detiene instantáneamente.
   - **Revalidación al Enfoque (`focus` / `visibilitychange`)**: Al regresar a la aplicación, se dispara de inmediato una consulta al muro social.
   - **Suspensión por Inactividad**: Tras 2 minutos continuos sin eventos de puntero o teclado, el sondeo entra en modo de reposo para economizar peticiones y batería.
   - **Actualización Táctil Manual**: Compatible con el componente gestual `PullToRefresh.tsx`.

3. **Paginación Basada en Cursor (`cursor_id`)**:
   Implementado en `app/crud/publicaciones_crud.py` para la consulta del muro social. A diferencia de la paginación por desplazamiento (`OFFSET`), que obliga a la base de datos PostgreSQL a escanear e ignorar filas anteriores a medida que avanza la página (complejidad $O(N)$), la paginación por cursor filtra directamente por clave primaria (`WHERE id < cursor_id ORDER BY id DESC LIMIT 15`). Esto aprovecha el índice B-Tree primario alcanzando una complejidad temporal constante $O(1)$ sin importar la profundidad del historial.

4. **Sincronización Atómica de Saldo de QuestCoins**:
   El método `updateBalance(delta)` expuesto en `AuthContext.tsx` permite a cualquier componente del cliente (ruleta, duelos, apuestas) actualizar localmente el saldo de QuestCoins de la interfaz sin ejecutar una llamada completa al perfil del usuario.

## Modelo Conceptual de Analogía: La Megafonía de la Plaza, el Tablón Efímero y la Guía Telefónica

Imagine la plaza principal del festival donde se anuncian las novedades del evento.

En una infraestructura fija con personal permanente en cabina, los altavoces del recinto (Server-Sent Events) transmiten las noticias en directo a todos los presentes sin necesidad de que nadie pregunte.

Sin embargo, si la organización opera mediante puestos de guardia temporales que se montan y desmontan en segundos (Serverless), mantener una megafonía continua no es viable. En su lugar, se habilita un tablón dinámico inteligente (Sondeo Reactivo): el participante consulta el tablón a intervalos de 15 segundos, pero solo si tiene los ojos abiertos mirando hacia él (pestaña activa). Si el asistente se echa la siesta o camina hacia otra zona (pestaña en segundo plano o inactividad), no gasta energía comprobando el tablón hasta que vuelve a mirar hacia él.

Para consultar el registro histórico de retos pasados, en lugar de hojear un libro desde la página 1 contando 1.000 líneas para llegar a la página deseada (paginación por OFFSET), el participante utiliza un marcador de índice exacto con el número de página anterior (paginación por Cursor), abriendo el libro directamente en la sección solicitada sin perder tiempo.

```mermaid
    autonumber

    participant Controller as Controlador POST /api/feed
    participant DB as Base de Datos PostgreSQL

    Cliente->>Broadcaster: GET /api/feed/stream (Conexion persistente SSE)
    Broadcaster-->>Cliente: EventStream OK (ping periodico)
    
    Note over Cliente,DB: Publicacion de un nuevo reto
    Cliente->>Controller: POST /api/feed/ (Crear mensaje)
    Controller->>DB: INSERT INTO publicaciones
    DB-->>Controller: Registro confirmado (ID asignado)
    Controller->>Broadcaster: broadcast("new_post", payload)
    Broadcaster-->>Cliente: Trama SSE data: {"type": "new_post", ...}
```
