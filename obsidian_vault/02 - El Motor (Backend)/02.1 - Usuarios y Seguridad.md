## Análisis Técnico: Gestión de Perfiles y Autenticación

### 1. Modelo de Datos (`Usuario` y `LedgerTransaccion`)
En `app/models/usuario.py` se definen las entidades de persistencia:
- **Modelo `Usuario`**: Almacena atributos principales como `id`, `username` (campo único e indexado), `password_hash`, `rol`, `saldo_actual` (medido en **QuestCoins**), `bio` y `avatar_url`.
- **Restricciones de Dominio (`CheckConstraint`)**:
  - `check_rol_valido`: Restringe los valores del campo `rol` a las cadenas `'admin'` o `'player'` ([[06.7 - Control de Acceso Basado en Roles|Modelo RBAC]]).
  - `check_saldo_positivo`: Impone la condición `saldo_actual >= 0`, impidiendo a nivel de base de datos la existencia de saldos negativos de QuestCoins.
- **Historial Contable (`LedgerTransaccion`)**:
  Cada variación de saldo genera una entrada inmutable con los campos `cantidad`, `concepto`, `saldo_resultante` y `fecha_creacion` (UTC), proporcionando una [[06.11 - Transacciones Atomicas e Integridad Referencial|trazabilidad auditable]].

### 2. Criptografía y Firma de Tokens JWT
En `app/security.py` se implementa la seguridad de credenciales:
- **Transformación de Contraseñas**: Emplea `passlib.context.CryptContext` con el algoritmo [[06.6 - Hashing de Contraseñas y Algoritmo Bcrypt|Bcrypt]]. Las contraseñas nunca se almacenan en texto claro.
- **Generación de Tokens**: Utiliza la biblioteca `python-jose` para emitir [[06.5 - Autenticacion con Tokens JWT|Tokens JWT]] firmados mediante la clave secreta `SECRET_KEY` y el algoritmo `HS256`, con una caducidad fijada en 7 días (`ACCESS_TOKEN_EXPIRE_MINUTES = 60 * 24 * 7`).

### 3. Inyección de Dependencias de Seguridad (`FastAPI Depends`)
En `app/dependencies.py` se estructuran las funciones de intercepción:
- `get_current_user`: Extrae la cabecera `Authorization: Bearer <token>`, decodifica la firma del JWT y recupera la instancia del usuario desde PostgreSQL. En caso de token inválido o expirado, retorna un código de estado `401 Unauthorized`.
- `get_admin_user`: Dependencia encadenada que verifica que `current_user.rol == 'admin'`. Si no se cumple esta condición, interrumpe el procesamiento devolviendo un código de error `403 Forbidden`.

## Modelo Conceptual de Analogía: Sistema de Registro y Credenciales

Para entender la gestión de usuarios y seguridad, puede analizarse el sistema mediante la analogía de un carné de acreditación:

1. **La Ficha de Registro (`Usuario`)**:
   Al inscribirse en la plataforma, el sistema emite una ficha con el nombre de usuario y el saldo de QuestCoins. El carné clasifica al usuario en dos categorías de acceso:
   - **Pase de Jugador (`player`)**: Habilita la participación estándar en misiones, duelos, apuestas y muros sociales.
   - **Pase de Administrador (`admin`)**: Confiere credenciales de supervisión para validar pruebas, ajustar marcadores y gestionar la configuración del evento.

2. **La Caja Fuerte Auditable (`check_saldo_positivo` + `LedgerTransaccion`)**:
   El motor contable opera como un libro diario bancario. Cualquier ingreso o gasto de QuestCoins exige la creación de un asiento especificando el origen de los fondos, previniendo alteraciones no autorizadas.

3. **La Credencial Digital Temporal (Token JWT)**:
   Tras verificar el nombre de usuario y la contraseña, la plataforma entrega una credencial digital firmada válida por 7 días. El navegador presenta esta credencial en cada solicitud HTTP, permitiendo al servidor validar la identidad sin requerir la reintroducción de la contraseña.

## Decisiones de Arquitectura de Software

- **Adopción de Tokens JWT Autosuficientes (Stateless)**: Evita consultar la base de datos para verificar el estado de la sesión en cada petición HTTP, reduciendo la latencia de respuesta.
- **Restricción de Saldo a Nivel de Base de Datos (`CheckConstraint`)**: Previene condiciones de carrera (*race conditions*) cuando se procesan peticiones concurrentes de gasto de QuestCoins, garantizando que PostgreSQL aborte cualquier transacción que viole la norma de saldo positivo.
