## Procedimiento Tecnico de Ejecucion de Pruebas

Este manual detalla los procedimientos estandarizados para la ejecucion de la suite de pruebas bajo el paradigma E2E-First (End-to-End First) en el proyecto QuestFest, integrando Playwright para la interfaz y PWA, y Pytest con HTTPX para la API y el Ledger.

---

## Explicacion Tecnica y Analogia

### Explicacion Tecnica
El paradigma E2E-First prioriza la verificacion en los limites externos del sistema (contratos HTTP, sesiones con cookies HttpOnly, transacciones reales en base de datos y comportamiento de la interfaz de usuario) frente a pruebas unitarias aisladas. Se prohiben las pruebas unitarias creadas con posterioridad a la implementacion del codigo, erradicando aserciones tautologicas y pruebas detectoras de cambios. El aislamiento estricto solo se admite cuando va precedido de una matriz de modos de fallo (diseno adversarial pre-mortem). Toda ejecucion E2E debe generar un artefacto reproducible y medible.

### Analogia
En la inspeccion tecnica de un vehiculo de carreras, una prueba unitaria posterior equivale a medir una tuerca suelta en un banco de trabajo despues de haber montado el motor, asumiendo complacientemente que encaja. La prueba E2E equivale a poner el vehiculo en el circuito con dos pilotos reales compitiendo a maxima velocidad bajo la lluvia: evalua la traccion, el consumo real de combustible, los frenos y la estabilidad ante curvas cerradas de forma simultanea y veraz.

## 1. El Modelo E2E en Dos Niveles

QuestFest estructura sus pruebas automatizadas en dos niveles complementarios:

1. **Nivel 1: E2E de API y Ledger (Backend)**: Ejecutado con `pytest` y `httpx.AsyncClient` sobre transporte ASGI (`ASGITransport`). Valida la integridad referencial, el bloqueo pesimista en transferencias de QuestCoins y los contratos Pydantic v2 a velocidad de milisegundos sin levantar navegador.
2. **Nivel 2: E2E de Sistema y PWA (Frontend)**: Ejecutado con `Playwright`. Simula usuarios reales en dispositivos moviles emulados (Pixel 7 e iPhone 15), validando areas tactiles minimas de 48x48 px, modo offline mediante Service Workers y escenarios multi-actor concurrentes mediante contextos de navegador aislados.

## 2. Pruebas Frontend y PWA con Playwright

### Instalacion y Binarios:
```bash
cd frontend
npm install -D @playwright/test
npx playwright install chromium
```

### Ejecucion de Pruebas E2E de Navegador:
```bash
# Ejecutar todas las pruebas E2E en modo headless
npm run test:e2e

# Ejecutar con interfaz grafica de Playwright para depuracion visual
npm run test:e2e:ui

# Visualizar el reporte interactivo generado tras la ejecucion
npm run test:e2e:report
```

### Configuracion de Artefactos:
Playwright registra trazas completas (`.zip`), capturas de pantalla y grabaciones en video de pruebas fallidas en el directorio `frontend/test-results/`. Estos archivos binarios estan estrictamente excluidos de Git en el archivo `.gitignore`.

## 3. Pruebas Backend y Ledger con Pytest (SQLite Async en Memoria)

Para evitar la contaminacion de la base de datos de desarrollo y garantizar pruebas deterministas, la suite de backend utiliza una base de datos en memoria SQLite asincrona (`sqlite+aiosqlite:///:memory:`).

### Instalacion de Dependencias:
```bash
cd backend
pip install pytest pytest-asyncio httpx aiosqlite
```

### Ejecucion de Pruebas Backend:
```bash
# Ejecutar toda la suite de pruebas
python -m pytest tests/ -v

# Ejecutar pruebas transaccionales del Ledger
python -m pytest tests/test_ledger.py -v
```

## 4. Rubrica de Escenarios de Dificultad Media a Alta

Todo escenario de prueba E2E debe cumplir al menos 3 de los 4 criterios de complejidad:
1. **Multi-Actor**: Al menos 2 usuarios interactuando simultaneamente con sesiones y contextos independientes.
2. **Mutacion Contable en Ledger**: Verificacion estricta de saldo previo, operacion atomica y balance resultante de QuestCoins.
3. **Inyeccion de Fallos y Resiliencia**: Intentos de operaciones invalidas (claves incorrectas, saldos insuficientes) que deben ser rechazadas con codigos 400/401/403 sin alterar el estado.
4. **Transicion Multi-Estado**: Transicion encadenada a traves de al menos 3 estados consecutivos del ciclo de vida de la entidad.
