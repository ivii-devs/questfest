## Procedimiento Técnico de Despliegue en Producción

Este manual describe el flujo operativo para la puesta en producción del proyecto **QuestFest**, incluyendo el proxy inverso NGINX con terminación TLS/SSL, la orquestación mediante Docker Compose para producción y el flujo de integración continua en GitHub Actions.

---

## 1. Arquitectura de Despliegue en Producción

El entorno de producción se organiza mediante contenedores aislados coordinados por `docker-compose.prod.yml`:

1. **Proxy Inverso NGINX (`nginx`)**: Escucha en los puertos estándar 80 (HTTP) y 443 (HTTPS), desviando el tráfico frontend hacia el contenedor Next.js (`:3000`) y las rutas de API hacia el servidor FastAPI (`:8000`). Sobrescribe `X-Real-IP $remote_addr` y propaga `X-Forwarded-For` para la identificación segura de clientes en el limitador de tasa.
2. **Servicio Frontend Next.js 16 (`frontend`)**: Empaquetado mediante `frontend/Dockerfile` en una compilación multi-stage basada en `node:20-alpine`. Aprovecha la directiva `output: 'standalone'` para reducir la imagen final a ~120MB, ejecutando bajo el usuario no root `nextjs`. Recibe la variable `NEXT_PUBLIC_API_URL` como argumento de compilación (`args`) para incrustar la URL del backend directamente en el código compilado del cliente.
3. **Servicio Backend FastAPI (`backend`)**: Ejecutado sobre Uvicorn con soporte de proxy (`--proxy-headers --forwarded-allow-ips "*"`), conectado al pool asíncrono de PostgreSQL con verificación pesimista `pool_pre_ping=True` y reciclaje preventivo cada 1800 segundos.
4. **Soporte NGINX para Eventos SSE**: Incluye cabeceras de desinhibición de buffer (`proxy_buffering off`, `Connection: ""`, `proxy_read_timeout 86400s`) para permitir el streaming en tiempo real del feed sin interrupciones.
5. **Servicio Base de Datos PostgreSQL (`postgres`)**: Contenedor aislado con volúmenes persistentes (`postgres_prod_data`) para salvaguardar el historial de QuestCoins, auditoría y usuarios con sondeo de salud `pg_isready`.
6. **Servicio de Caché y Límites Redis (`redis`)**: Provee persistencia en memoria para el almacenamiento distribuido del Rate Limiter (`slowapi`).

## 2. Puesta en Marcha con Docker Compose de Producción

### Comando de Arranque:
```bash
# Compilar y arrancar la infraestructura completa de producción
docker-compose -f docker-compose.prod.yml up -d --build

# Verificar el estado de los contenedores
docker-compose -f docker-compose.prod.yml ps

# Aplicar migraciones de base de datos de producción (contenedor backend)
docker-compose -f docker-compose.prod.yml exec backend alembic upgrade head
```

## 3. Pipeline de Integración Continua (GitHub Actions)

El archivo `.github/workflows/ci.yml` automatiza la validación del código en cada push o pull request a las ramas `main` o `master`:

1. **Job `backend-test-and-lint`**: Configura un entorno Python 3.11, instala las dependencias de `requirements.txt` y ejecuta la suite automatizada de `pytest tests/ -v`.
2. **Job `frontend-lint-and-build`**: Configura un entorno Node.js 20, instala las dependencias con `npm ci`, valida el tipado y linter con `npm run lint` y compila la versión de producción con `npm run build`.

## 4. Control de Versiones en Git y Gestión Segura de Secretos

Para garantizar que el código se mantenga protegido y reproducible al alojarse en plataformas como GitHub:

1. **Aislamiento Estricto de Credenciales**:
   - Los archivos de entorno reales (`.env`, `backend/.env`, `frontend/.env.local`) contienen contraseñas de base de datos (`POSTGRES_PASSWORD`), claves secretas de JWT (`SECRET_KEY`) y tokens de Cloudinary. Están estrictamente ignorados en `.gitignore`.
2. **Plantillas Despersonalizadas (`.env.example`)**:
   - Se proporcionan archivos de ejemplo (`.env.example`, `backend/.env.example`, `frontend/.env.example`) que documentan exhaustivamente cada variable requerida sin exponer secretos reales.
3. **Exclusión de Entornos Virtuales, Dependencias y Scripts de Mantenimiento**:
   - El `.gitignore` raíz bloquea directorios masivos de ejecución local (`backend/venv/`, `frontend/node_modules/`, `frontend/.next/`, `.pytest_cache/`) y scripts de mantenimiento local (`backend/app/scripts/`), asegurando que solo el código fuente esencial y seguro sea versionado.
4. **Validación Estricta de Variables en Docker Compose (`${VAR:?Error}`)**:
   - En `docker-compose.prod.yml` se utiliza la sintaxis de sustitución obligatoria `${POSTGRES_PASSWORD:?Error}` y `${SECRET_KEY:?Error}`. Esto erradica contraseñas de contingencia (*fallbacks*) en texto plano dentro del repositorio, forzando a que la orquestación aborte inmediatamente con un mensaje explícito si el archivo `.env` de producción no está configurado.
